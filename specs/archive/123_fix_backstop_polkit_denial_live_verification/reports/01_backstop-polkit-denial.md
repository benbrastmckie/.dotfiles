## Executive Summary

- **A (mechanism)**: `security.polkit.extraConfig` is the correct, idiomatic, and already-precedented mechanism in this exact nixpkgs tree — three other in-tree modules (`automatic-timezoned.nix`, `fwupd.nix`, `networkmanager.nix`) use it for the same shape of problem (grant one action to one subject). It does **not** create a new `rules.d` file; NixOS's `polkit.nix` concatenates `cfg.extraConfig` verbatim into the *body* of the same file the system already ships, `/etc/polkit-1/rules.d/10-nixos.rules`. There is therefore no numeric-prefix conflict to reason about on this host today (it is the only `.rules` file present), and a narrowly-scoped custom rule (root + `suspend-ignore-inhibit` only) is trivial to write this way — the shipped `.example` is NOT the recommended vehicle here because narrowing it means editing its text, not symlinking it.
- **B (alternatives)**: The `/sys/power/state` and different-D-Bus-call alternatives were evaluated and rejected. Root can already write `/sys/power/state` directly (verified: `-rw-r--r-- root root`), which is *more* privileged and *less* safe than the polkit rule — it skips logind's entire sleep sequence (`/usr/lib/systemd/system-sleep` pre/post hooks, `user.slice` freeze, delay-inhibitor honoring) entirely, whereas `systemctl suspend -i` still goes through that sequence and only overrides *block* inhibitors. "Stop the inhibitors then call plain `systemctl suspend`" is rejected because it is destructive to the very state (Claude Code's live agent sessions) the inhibitor exists to protect, and evidence below shows plain `suspend` (no `-i`) would likely still be polkit-denied for this session-less root caller regardless. The polkit rule is confirmed as the right answer, not rubber-stamped.
- **C (verification)**: `pkcheck` gives a genuine agent-runnable, no-`sudo`, read-only probe of the *current* authorization state, and it was run live in this session, reproducing the exact denial (`polkit.result=auth_admin_keep`, exit 2) without touching `systemctl`. However, a hard polkit security boundary (confirmed live) means this probe **cannot** be used by an unprivileged agent to ask "would `root` specifically be authorized" — polkit refuses `CheckAuthorization()` for any subject other than the caller's own real identity unless the caller is already trusted (uid 0). This means the single fully faithful end-to-end check — did `systemctl suspend -i` actually get authorized and actually suspend — remains irreducibly a `sudo`/user-only step, exactly matching the established-fact-3 probe shape. A second, much lower-risk `sudo` check (`pkcheck` run *as root*, no suspend) is proposed as an intermediate step the user can run before committing to a real suspend cycle.
- **D (test-suite hardening)**: There is currently **no committed test file** for this component anywhere in the repository (confirmed by search) — the "23/23 assertions" offline suite referenced in task 117's history is an ephemeral scratchpad script, explicitly noted as "not committed to the repo" in `handoffs/phase-6-handoff-20260725.md`. That is itself a gap independent of the stubbing question. Recommendation: commit a small, versioned smoke-test script that (1) documents the stub-covers-logic-only caveat inline, and (2) adds one new non-stubbed, no-`sudo` assertion using the caller's-own-identity `pkcheck` regression check from C, which *can* be automated and would have caught neither original defect by itself but closes the "nobody re-reads the caveat" risk for the next round.
- **E (risk)**: The delta from granting root `suspend-ignore-inhibit` is real but narrow and net-positive: it lets root skip *sleep block inhibitors specifically for suspend*, nothing else, and only for a caller already possessing unlimited system access. Root already has an unconditionally stronger, hook-skipping path (`/sys/power/state`) with zero authorization gate today, so the rule closes a gap in *capability* the safety net needs, while adding no new *privilege* root doesn't already have via a rougher route. No other root-run service on this host currently calls suspend, reboot, halt, hibernate, or power-off (checked: only `battery-suspend-backstop` references `systemctl suspend` in the whole repo).

## Context & Scope

Task 117 (rounds 1-3) built and activated a `battery-suspend-backstop` oneshot+timer in `modules/system/power.nix` that suspends the laptop at <=10% battery, discharging, bypassing Claude Code's sleep-block inhibitors via `systemctl suspend -i`. Round 3's live post-activation checklist (USER CHECKLIST item 3b, see `specs/117_.../summaries/05_backstop-grace-and-live-verification-summary.md`, "Second post-activation round") found this call is **denied by polkit** in production: the session-less root oneshot has no cached admin authentication and no agent to prompt, so `org.freedesktop.login1.suspend-ignore-inhibit` (which ships with `auth_admin_keep` on all three subject classes) is refused every time. That round also found and fixed a `runuser -u "#$uid"` defect in the notify helper, and recorded that **both** defects were invisible to the offline test suite because `BACKSTOP_SYSTEMCTL_BIN` / `BACKSTOP_NOTIFY_BIN` env-var stubs replace the real binaries during that suite's run.

This report answers five questions: the correct Nix mechanism for the polkit fix (A), whether a non-polkit alternative is actually better (B), how to verify the fix live without `sudo` in an agent context and what must fall to the user (C), how to harden the test suite against this class of blind spot (D), and whether the fix has a real security cost (E). All established facts in the task prompt are treated as given; this report only re-derives what wasn't already stated, and calls out every claim's evidence.

## Findings

### A. Correct NixOS mechanism

- **How `security.polkit.extraConfig` actually lands on disk** (read from `/nix/store/l7a68lamx41wiwya8qc7aaby16rnpsh4-.../nixos/modules/security/polkit.nix:85-91`):
  ```nix
  environment.etc."polkit-1/rules.d/10-nixos.rules".text = ''
    polkit.addAdminRule(function(action, subject) { return [...cfg.adminIdentities]; });
    ${cfg.extraConfig}
  '';
  ```
  `extraConfig` is **appended inside the same file NixOS already owns**, `10-nixos.rules` — confirmed live: `/etc/polkit-1/rules.d/10-nixos.rules` is a symlink to `/etc/static/polkit-1/rules.d/10-nixos.rules`, itself resolving to `/nix/store/x1w1ikkg5qfpx11wqyqlmyq136ymqj2w-etc-polkit-1-rules.d-10-nixos.rules`, whose live content (`cat`'d this session) currently contains exactly the `addAdminRule` block plus five `addRule` blocks for `automatic-timezoned`, cups, NetworkManager (x2), and `fwupd-refresh` — the same pattern this fix should follow. `ls -la /etc/polkit-1/rules.d/` shows this is the **only** file in the directory on this host.
- **Precedent in this exact nixpkgs closure**: `automatic-timezoned.nix:37-44` uses the identical idiom this fix needs:
  ```nix
  security.polkit.extraConfig = ''
    polkit.addRule(function(action, subject) {
      if (action.id == "org.freedesktop.timedate1.set-timezone"
          && subject.user == "automatic-timezoned") {
        return polkit.Result.YES;
      }
    });
  '';
  ```
  `fwupd.nix` and `networkmanager.nix` (`polkitConf` at line 697) do the same for their own actions. This is the module system's own established pattern for "grant exactly one action to exactly one subject," which is exactly this task's shape.
- **Recommended narrow snippet** for `modules/system/power.nix` (mirrors the precedent above and the shipped `.example`'s `subject.user == "root"` check, but narrowed to the single action this repo needs):
  ```nix
  security.polkit.extraConfig = ''
    // Allow root to suspend while ignoring inhibitors, for the session-less
    // battery-suspend-backstop oneshot (task 123). Scoped to root and to
    // suspend only -- NOT the other four *-ignore-inhibit actions the
    // upstream .example grants (power-off/reboot/halt/hibernate), which
    // this repo does not need.
    polkit.addRule(function(action, subject) {
      if (action.id == "org.freedesktop.login1.suspend-ignore-inhibit" &&
          subject.user == "root") {
        return polkit.Result.YES;
      }
    });
  '';
  ```
  This can live in `modules/system/power.nix` itself (where `security.polkit.enable = true` is set today, `modules/system/desktop.nix:100`) or directly in `power.nix` next to the backstop unit — either way it merges into the same `10-nixos.rules` file, so there is no cross-file ordering question to resolve for this specific change.
- **`rules.d` numeric-prefix precedence — does it matter here?** From `man polkit` (AUTHORIZATION RULES / "The Polkit type" sections), confirmed independently via WebSearch against the upstream polkit.8 manpage:
  - Rule files are read from `/etc/polkit-1/rules.d`, `/run/...`, `/usr/local/share/...`, `/usr/share/...`, in that directory order, and within/across that set, in **lexical order of basename** (tie -> earlier directory wins).
  - `addRule()` callbacks are invoked **in the order they were registered** (i.e., file order, then within-file order) **until one returns a non-`NOT_HANDLED` value** — first definite answer wins, later callbacks are never even called for that check. ("There is no guarantee that a function registered with `addRule()`... is ever called - for example an early rules file could register a function that always returns a value.")
  - Because this fix's rule lives **inside** `10-nixos.rules` (via `extraConfig`), and that file is the *only* `.rules` file present on this host, there is **no conflict today**. The only way this could ever matter is if some future NixOS module or manually-dropped file created a separate `.rules` file that sorts lexically before `10-nixos.rules` (e.g., `00-*.rules` or `05-*.rules`) and that file's `addRule` already returns a definite value for `org.freedesktop.login1.suspend-ignore-inhibit` before evaluation ever reaches ours — grep of this repo's Nix files found no such file. This is worth a one-line code comment (see recommendation) but is not a live risk.
  - Contrast: had the fix instead used `environment.etc."polkit-1/rules.d/10-systemd-logind-root-ignore-inhibitors.rules".source = "${pkgs.systemd}/share/polkit-1/rules.d/10-systemd-logind-root-ignore-inhibitors.rules.example";` (literally symlinking the shipped file, as its own header comment instructs), that *would* create a second file. Lexical comparison `"10-nixos.rules"` vs `"10-systemd-logind-root-ignore-inhibitors.rules"`: `"10-n"` sorts before `"10-s"`, so `10-nixos.rules` would still be evaluated first — harmless here since it contains no login1 rule, but this is exactly the kind of ordering reasoning `extraConfig` avoids by construction. It would also grant all **five** `*-ignore-inhibit` actions (power-off, reboot, halt, suspend, hibernate) rather than just the one this repo needs, working against the task's explicit ask to narrow scope.
  - **Conclusion**: `security.polkit.extraConfig` with the narrow custom rule above is preferred over an `environment.etc` symlink to the `.example` file, on both narrowing grounds (explicitly requested) and idiom grounds (matches three sibling in-tree modules already doing the same thing for the same shape of problem).

### B. Alternatives to the polkit grant

- **(i) Kill/stop the inhibitors, then call plain `systemctl suspend`.** Rejected. The whole point of the backstop (per `power.nix`'s own banner comment, lines ~207-213) is that Claude Code's `sleep:idle`/block inhibitors must be preserved for every other purpose (headless agents keep running) and only bypassed for this one narrow, battery-protective decision. Actively stopping/killing the inhibitor holders to permit suspend would kill or corrupt in-flight agent sessions — the opposite of task 117's design intent, and a strictly worse failure mode than an authenticated bypass. Not evaluated further as it fails on intent grounds alone, independent of logind semantics.
  - Also relevant: plain (non-`-i`) `systemctl suspend` for `org.freedesktop.login1.suspend` has `allow_active = yes` but `allow_any = auth_admin_keep` / `allow_inactive = auth_admin_keep` (read from `org.freedesktop.login1.policy`). The backstop's caller is a session-less root oneshot, not an active local session, so it falls under `allow_any` — meaning even *without* inhibitors, a plain `systemctl suspend` from this exact caller shape would likely **also** hit an `auth_admin_keep` wall (distinct from, but structurally identical to, the `-i` defect this task fixes). This is consistent with, not contradicted by, the round-3 finding that plain `sudo systemctl suspend` was refused with `BlockedByInhibitorLock` rather than a polkit prompt — that refusal short-circuits earlier for a different reason (an active inhibitor lock), and does not prove plain suspend would clear polkit on its own for this caller.
- **(ii) Write directly to `/sys/power/state`.** Rejected as *worse*, not merely equivalent. Verified live: `/sys/power/state` is `-rw-r--r-- root root` (mode 644) — only root can write it, confirming the established fact that root already has an unconditional path to suspend with **zero** authorization gate, today, with no code change needed. But per `man systemd-suspend.service` (read locally): `systemd-suspend.service` is what actually performs the `echo mem > /sys/power/state` step, and it does so only **after** running every executable in `/usr/lib/systemd/system-sleep/` with `pre suspend`, freezing `user.slice`, and honoring registered delay-inhibitors, then reversing that sequence (`post suspend`) on resume. A raw sysfs write from the backstop script would skip *all* of that: no pre-sleep hooks run, no delay-inhibitors get their grace period, `user.slice` is not frozen first. This is a strictly larger blast radius than accepting a polkit grant that only lets root skip *block* inhibitors while keeping the rest of logind's sequence intact. Recommendation stands: do not use this path.
- **(iii) A different D-Bus call/auth semantics.** `systemctl suspend -i` already *is* the D-Bus call with the "different" (ignore-inhibitors) semantics — `login1`'s `Suspend()` method takes an `interactive`/flags argument, and the `-i` flag specifically requests `SD_LOGIND_SKIP_INHIBITORS`, which is precisely why it maps to the separate, stricter `suspend-ignore-inhibit` action rather than plain `suspend`. There is no third D-Bus surface that skips inhibitors with looser default auth; the two-action split (plain vs. ignore-inhibit) *is* logind's chosen "different auth semantics" mechanism, and the task's current call already selects the correct one. No further alternative to evaluate here.
- **Conclusion**: the polkit rule is confirmed, not merely assumed. It is the only evaluated option that (a) keeps logind's full sleep sequence (hooks, freeze, delay-inhibitor honoring) intact, (b) does not require destroying the very inhibitors the mechanism exists to respect elsewhere, and (c) adds no privilege root doesn't already have via a rougher, hook-skipping route.

### C. Live, non-stubbed verification design

**What was actually run this session (agent-side, no `sudo`, all read-only):**

- `pkcheck --action-id org.freedesktop.login1.suspend-ignore-inhibit --process "$$"` (own shell, real uid 1000, no override) -> `polkit.result=auth_admin_keep`, exit 2. This independently reproduces the *shape* of the established-fact-3 denial without invoking `systemctl` at all.
- Attempted to use `pkcheck`'s `PID[,START_TIME,UID]` override to simulate checking *as root* without `sudo`: `pkcheck ... --process "$$,,0"` and `--process "$$,,99999"` both returned **byte-identical** output to the unmodified call (`auth_admin_keep`, exit 2) — the UID field of the override is not honored for an untrusted caller; polkit re-derives the subject's real identity from `/proc` for the given PID regardless of the supplied override.
- Attempted the same probe against an actual root-owned process (`--process "1"`, systemd/PID 1, real uid 0): this failed outright with `GDBus.Error:...NotAuthorized: Only trusted callers (e.g. uid 0 or an action owner) can use CheckAuthorization() for subjects belonging to other identities`, exit 127.
- **Finding (load-bearing for the whole verification design)**: an unprivileged agent process **cannot** ask polkit "would `root` be authorized for this action" — not via `pkcheck`, not via any equivalent D-Bus `CheckAuthorization()` call — because polkit itself refuses cross-identity authorization checks from untrusted callers. This is a hard boundary, not a tooling limitation to work around. It means the single fully faithful reproduction of the production failure mode (root, session-less, calling `suspend -i`) is irreducibly a `sudo`/root-context operation, matching exactly the shape of the `sudo systemd-run --pipe ...` probe already used to establish this defect (established fact 3).

### E. Security delta of the grant

- **What is granted**: `subject.user == "root"` for exactly one action, `org.freedesktop.login1.suspend-ignore-inhibit`. This lets root's D-Bus caller instruct logind to run the full normal suspend sequence while skipping *block*-type sleep inhibitors. It does not grant power-off, reboot, halt, or hibernate ignore-inhibit (unlike the upstream `.example`, deliberately narrowed per A/task ask), and it does not touch delay-inhibitor semantics (delay-inhibitors still get their grace window; only block-inhibitors are skipped, which is inherent to logind's ignore-inhibitors design, not something the polkit rule additionally controls).
- **What else runs as root that could now (mis)use this**: grep of every `*.nix` file in this repo for `systemctl suspend`, `SuspendWithFlags`, and `ignore-inhibit` found exactly one hit outside `power.nix` itself (`modules/home/desktop/swaylock.nix`, unrelated — a pre-lock hook, does not call suspend). No other systemd unit, cron/timer, or script in this configuration invokes suspend, so the practical exposure is exactly the one call site this task is fixing, not a general new capability handed to "root" as an abstract actor.
- **Is this a real delta given `/sys/power/state` is already root-writable?** Argued in B above and reaffirmed here: no. Root already has an *unconditional*, hook-skipping path to force the machine to sleep with zero authorization check, live and unaffected by this task either way (verified `-rw-r--r-- root root`, mode 644 on `/sys/power/state`). Granting root the *narrower*, *hook-preserving* `suspend-ignore-inhibit` action does not create a new capability class for "root can suspend the machine" — that capability already exists, unconditionally, via the sysfs write. It changes *which* of root's two suspend paths this specific script uses, from a nonexistent/denied one to the properly-sequenced one. If anything, encouraging use of the polkit-gated, hook-preserving path over the raw sysfs write is the safer direction, not a new risk.
- **Residual consideration**: `auth_admin_keep` normally exists to require interactive re-authentication periodically; removing that requirement specifically for root is standard practice for exactly this class of headless-automation problem (it's the literal purpose systemd ships the `.example` for), and is scoped to a single-user laptop where "root" is not a distinct trust boundary from the machine owner (there is one wheel-group human, `benjamin`, per `10-nixos.rules`' `addAdminRule` returning `["unix-group:wheel"]`). No multi-tenant or shared-machine risk model applies here.

## Decisions

- Use `security.polkit.extraConfig` in `modules/system/power.nix` (not `environment.etc` / not symlinking the `.example`) — matches in-tree precedent, avoids new-file ordering questions, and allows narrowing to `suspend-ignore-inhibit` only, unlike the shipped `.example` which grants all five `*-ignore-inhibit` actions.
- Scope the rule to `action.id == "org.freedesktop.login1.suspend-ignore-inhibit" && subject.user == "root"` — exact equality on both fields, mirroring the `automatic-timezoned` precedent's style.
- No non-polkit alternative is adopted; the polkit rule is confirmed as correct after evaluating inhibitor-teardown, raw-sysfs, and D-Bus-semantics alternatives.
