## Executive Summary

- The three mechanisms stated as "already proven" in the task brief are confirmed consistent
  with systemd's documented behavior, and this research adds the specific missing details
  needed to implement them safely: `--pty` is **invalid in combination with `--scope`** (and
  unnecessary — a scope inherits the caller's controlling terminal directly, no PTY
  reallocation involved), cwd/env/exit-code all propagate through `--scope` with **no extra
  flags**, and `--unit=` values get `.scope` auto-appended by `systemd-run` itself.
- Recommended unit-naming scheme: `claude-$$-$(date +%s)` (own PID + timestamp), generated by
  the wrapper script itself — not derived from the CLI's internal session ID, which does not
  exist yet at the moment the wrapper execs.
- The reap predicate should walk `systemctl --user list-units --type=scope --all
  'claude-*.scope'`, read each unit's `cgroup.procs`, and check membership against a
  claude-process signature — **scoped to PIDs already inside that specific unit's cgroup**,
  never a system-wide process scan, satisfying the "must not enumerate arbitrary processes"
  constraint literally as well as in spirit.
- The reaper is a straightforward oneshot-service + timer home-manager module, directly
  modeled on the two existing precedents in this repo (`cache-cleanup.nix`,
  `mail-sync-timer.nix`); a third precedent (`gmail-oauth2.nix`, now disabled) is a documented
  cautionary tale about a periodic unit that degraded the whole user systemd session by
  failing every run — the reaper must tolerate errors (`|| true` around inspection code) so it
  can never do that.
- The opt-out for deliberately-detached work falls out of the design for free: anything
  launched as its own independent transient unit (`systemd-run --user --unit=<name> -- cmd`,
  a plain unit name, not matching `claude-*.scope`) is never touched by the reaper and never
  wrapped, because the reaper's unit glob and the wrapper's containment are both scoped
  strictly to the `claude-*.scope` naming pattern.
- No conflict found with the existing `SessionStart`/`SessionEnd` sleep-inhibitor hook pair —
  it operates on an unrelated PID-file mechanism keyed by the CLI's own `session_id` (only
  known after the CLI starts), while the scope wrapper's unit ID is generated by the wrapper
  *before* exec, so the two never need to share an identifier.

## Context & Scope

Task 125 asks for two changes:
1. Wrap every `claude` invocation (`packages/claude-code.nix`) in a systemd `--user --scope`
   so all descendants — including detached/double-forked children and MCP server
   subprocesses — are contained in one per-session cgroup.
2. Add a reaper (home-manager systemd user timer + oneshot service) that finds and kills
   scopes whose owning claude session is gone, using a liveness-only predicate, never a
   CPU/memory/wall-clock threshold, and never touching anything outside the `claude-*.scope`
   naming pattern.

The mechanism (scope containment works even for double-forked children; `systemctl --user
stop` SIGKILLs everything left in a scope; an abandoned scope is detectable by checking
`cgroup.procs` for a live `claude` process) is stated as already empirically verified on this
host and was treated as ground truth, not re-derived. This research instead focused on the
specific open questions the task called out: TTY/interactive correctness of `--scope`, unique
unit naming, nested-invocation behavior, unit-type choice, home-manager conventions for the
reaper, the opt-out, hook interaction, and other breakage risk.

  **never** run that pattern as a system-wide `pgrep`. It must first collect the specific PID
  set from one scope's `cgroup.procs` (a small, already-authorized set of processes that live
  inside a `claude-*.scope` unit the reaper is specifically inspecting) and only then check
  whether *any* of those specific PIDs' `/proc/<pid>/cmdline` matches the pattern. This
  keeps the "never enumerate/kill arbitrary user processes" constraint intact at the
  mechanism level, not just by convention.

- **`docs/no-sleep-agents.md`** documents the existing `SessionStart`/`SessionEnd` hook pair

  wrapper needs: the hook's `SESSION_ID` is only known once the CLI process is already
  running and has fired `SessionStart`, whereas the scope's `--unit=` name must be chosen
  *before* `exec`ing the CLI at all (systemd-run wraps the exec, not something the CLI does to
  itself). The two mechanisms are independent and do not need to share an identifier — no
  coordination or naming collision is required, and this research does not recommend
  threading the CLI's `session_id` back to the wrapper (it can't be, at the point the wrapper
  runs).

### Nix / systemd Documentation and Live Verification

**TTY / interactive correctness — the critical open question:**

The `systemd-run(1)` man page states that a `--scope` invocation "will be executed by
`systemd-run` itself as parent process and will thus inherit the execution environment of the
caller," and separately documents that `--pty` (which reconnects stdio to the terminal via a
*new* pseudo-TTY) is meant for **service** units, which are otherwise forked/managed by the
systemd manager and do not have a controlling terminal at all unless told to acquire one.
`--pty` is explicitly **not combinable with `--scope`** — trying to pass both is an error.

Practically, this means: for `--scope`, `systemd-run` is a normal foreground child of the
invoking shell, and the wrapped program is in turn a normal foreground child of `systemd-run`
— a completely ordinary UNIX process tree with the terminal already attached via inherited
file descriptors 0/1/2. There is no PTY reallocation, no session detachment performed by
`systemd-run` itself, and no service-manager indirection. This is why the task's proven test
#1 ("even a `setsid nohup` double-forked child" landed in the scope's cgroup) worked exactly
as expected — the parent (`systemd-run`) and its exec'd child are ordinary processes under the
manager's tracked cgroup, regardless of how the child later reparents itself.

**Recommendation**: use plain `systemd-run --user --scope --unit=<name> -- <cmd> "$@"` with
**no `--pty`**. Adding `--pty` would either error outright (invalid with `--scope`) or, if the
flag combination were ever silently accepted in some systemd version, would be actively wrong
— it would insert an unnecessary new PTY layer for a foreground app that already has a
perfectly good controlling terminal.

**Verified live on this host** (small scoped tests run during this research session, not
re-deriving the already-proven mechanism, only confirming the wrapper-relevant details the
task brief didn't already establish):

```
$ systemd-run --user --scope --unit=test-research-check-$$ -- echo hello
Running as unit: test-research-check-2590276.scope; invocation ID: ...
hello
```
- `--unit=foo` becomes unit `foo.scope` — `systemd-run` appends the suffix itself. The
  reaper's unit glob must be `'claude-*.scope'`, not `'claude-*'`.

```
$ cd /tmp/scopetest && systemd-run --user --scope --unit=test-cwd-$$ -- pwd
/tmp/scopetest
```
- Current working directory is inherited with **no flag needed** (no `--same-dir`/`-d`
  required). This matters because users routinely `cd` into a project before running
  `claude`; a wrapper that silently reset cwd to `$HOME` or `/` would be a serious regression.

```
$ FOO_TEST_VAR=bar123 systemd-run --user --scope --unit=test-env-$$ -- printenv FOO_TEST_VAR
bar123
```
- Arbitrary environment variables are inherited with no `-E/--setenv` needed.

```
$ systemd-run --user --scope --unit=test-exit-$$ -- bash -c "exit 37"; echo $?
37
```
- The wrapped program's exit code propagates back through `systemd-run --scope` unchanged
  (documented generically in EXIT STATUS as "propagated from the service," confirmed here for
  scope mode specifically). `claude`'s own exit code (used by any caller checking `$?`) is
  preserved.

**Not fully verified live** (flag for the task's own required live-verification step, which
already calls for launching a real interactive session and confirming orphan cleanup — the
same session should also exercise these): process-group/session semantics for signal
delivery. The man page does not document whether the scope's exec'd child ends up in the same
process group as the invoking terminal's foreground job (relevant to raw kernel-level Ctrl-C/
Ctrl-Z delivery via the tty line discipline). In practice this is very unlikely to matter for
`claude` specifically, since interactive terminal AI CLIs of this kind put the terminal into
raw mode and handle Ctrl-C/Ctrl-Z as literal input bytes themselves rather than relying on
kernel-delivered `SIGINT`/`SIGTSTP` — but this should be confirmed as part of the live
smoke test (press Ctrl-C during a running turn, Ctrl-Z, resize the terminal) before treating
the wrapper as safe to enable unconditionally.

**Nested invocation (claude spawning claude):**

Nothing in this repo's hooks/scripts currently launches a nested `claude` CLI process from
within a running session (subagents run in-process via the Task/Agent tool, not as new OS
processes) — but a user could still manually run `claude` again from inside a Bash tool call.
Because the wrapper generates a fresh, PID-based unit name on every invocation (see below),
this is not a naming collision risk. The interesting cgroup-mechanics question is what happens
when the *inner* `systemd-run --user --scope` runs from a process whose own cgroup is already
`claude-<outer>.scope`: cgroup v2's "no internal process" rule only forbids a cgroup from
holding both processes and child cgroups simultaneously — it does not forbid *migrating* a
process between two sibling leaf cgroups. `systemd-run --scope` performs exactly that kind of
migration (move the target PID into the new unit's cgroup), so the inner `claude` process
would simply move itself out of the outer scope's cgroup and into its own new
`claude-<inner>.scope`. This is an acceptable, self-consistent outcome: the inner session gets
independent containment and independent reaper coverage; it stops being a member of the outer
scope, so killing the outer scope later will not reach it (and vice versa) — each session's
lifecycle is judged purely by its own liveness, which matches the reap predicate's design
intent. Document this as expected/benign behavior, not a bug, if it's ever observed.

**Unit type choice — scope vs. service vs. slice:**

Scope is correct, and the task brief's own proven test already validates it as the right
primitive (not a fresh design question): scopes are specifically for *externally forked*
process trees that a manager didn't create itself, which is exactly the wrapper's situation
(`systemd-run` execs the process directly, then hands the resulting cgroup to the user
manager for tracking). A service unit would require the systemd manager itself to fork the
process (implying `--pty` for terminal reattachment, more indirection, and a real question
about whether stdio semantics would differ subtly). A slice is a pure grouping/accounting
node with no process-management semantics of its own (no `stop` action that kills members
directly) — wrong tool for a unit that needs to be killed as a whole.

**Reap predicate and reaper mechanics:**

Recommended algorithm, run once per timer tick:
1. `systemctl --user list-units --type=scope --all --no-legend --plain 'claude-*.scope'`
   — this is the **only** enumeration surface the reaper touches; the naming-pattern glob is
   the hard boundary that satisfies "MUST only ever act on units matching the claude scope
   naming pattern."
2. For each matched unit, resolve its cgroup path:
   `systemctl --user show <unit> -p ControlGroup --value`, then read
   `/sys/fs/cgroup<that-path>/cgroup.procs` (a plain newline-separated PID list; empty file
   if no processes remain). Wrap this read in `|| true` / existence checks — the unit may
   have already transitioned to fully inactive between the `list-units` call and this read
   (races are expected and must be treated as "nothing to reap," not an error).
3. If `cgroup.procs` is empty: nothing to kill; optionally `systemctl --user reset-failed
   <unit>` for tidiness (see `--collect` note below) and move on.
4. If `cgroup.procs` is non-empty: for **each PID already in that list only**, check
   `/proc/<pid>/cmdline` (fall back to `/proc/<pid>/comm` if `cmdline` is empty, e.g. a
   kernel thread edge case that shouldn't occur here but costs nothing to guard) against a
   claude-process signature. Reuse the substring family already used elsewhere in this repo
   for the same purpose (`modules/home/memory/monitor.nix`'s
   `(claude|@anthropic|opencode)`), narrowed here to only the PIDs already known to live
   inside this specific `claude-*.scope` unit's cgroup — never a system-wide `pgrep`.
5. If **any** PID in that scope matches the signature: the owning session is still alive.
   Skip this unit entirely — no inspection of CPU time, RSS, or start time is performed, and
   none should be added later; this is the literal implementation of the "liveness-only,
   never a threshold" constraint.
6. If **none** match: the scope is abandoned. `systemctl --user stop <unit>` — already
   verified (task brief, mechanism 2) to SIGKILL every remaining process in the cgroup, which
   is exactly the runaway-`python3`/orphaned-lean-lsp-worker case this task exists to fix.
   Follow with `systemctl --user reset-failed <unit>` to clear the unit from
   `systemctl --user list-units` afterward.

**`--collect` note**: `systemd-run --collect` (equivalently `CollectMode=inactive-or-failed`
set on the transient unit) is documented generically for "transient units" as "unload the
transient unit after it completed, even if it failed," with no explicit scope-vs-service
carve-out found in the man page. Passing `--collect` when creating the scope in
`packages/claude-code.nix` would let *cleanly completed* sessions (all children exited,
cgroup naturally empty) disappear from `systemctl --user list-units` on their own, so the
reaper's `reset-failed` step in step 3 above becomes a pure belt-and-suspenders no-op for the
common case, only doing real work for the crashed/abandoned case in step 6. This should be
confirmed empirically during implementation (create a scope with `--collect`, let the wrapped
command exit normally, confirm the unit vanishes from `list-units` without any reaper
involvement) rather than assumed, since the man page's silence on the scope-specific case
leaves some doubt — but it is not load-bearing for correctness either way, since the reaper's
own `list-units` + `cgroup.procs` check is authoritative and self-contained regardless of
whether `--collect` is also set.

### Home Manager / Nix Implementation Shape

**`packages/claude-code.nix`** — proposed replacement:

```nix
{
  writeShellScriptBin,
  nodejs,
}:

writeShellScriptBin "claude" ''
  # Contain this session — and every descendant it spawns, including detached/
  # double-forked children and MCP server subprocesses — in its own systemd --user
  # scope, so nothing from this session can outlive it as an untracked orphan.
  # See specs/125_claude_session_scope_containment_and_reaper/reports/01_*.md.
  if command -v systemd-run >/dev/null 2>&1 && [ -n "''${XDG_RUNTIME_DIR:-}" ]; then
    UNIT="claude-$$-$(date +%s)"
    exec systemd-run --user --scope --unit="$UNIT" --quiet \
      -- ${nodejs}/bin/npx @anthropic-ai/claude-code@latest "$@"
  else
    exec ${nodejs}/bin/npx @anthropic-ai/claude-code@latest "$@"
  fi
''
```

Notes on this shape:
- `$$` (the wrapper script's own PID) is guaranteed unique among currently-live processes;
  appending `date +%s` additionally avoids a `--unit=` name collision against a *stale,
  not-yet-reset-failed* unit left over from a previous, already-dead process that happened to
  reuse the same PID.
- The `command -v systemd-run` / `XDG_RUNTIME_DIR` guard is a fallback, not present in the
  task's proven-mechanism list but recommended here as a safety measure specific to this file:
  unlike the reaper (a periodic background timer where a failure is contained to one skipped
  tick), this wrapper gates *every single* `claude` launch. If it ever ran in a context without
  a working `--user` systemd manager (headless SSH without lingering enabled, a minimal
  container, etc.), a hard dependency on `systemd-run` succeeding would make it impossible to
  start Claude Code at all — a much larger blast radius than the gmail-oauth2 precedent's
  degraded-session symptom. The existing `SessionStart` hook already depends on
  `systemd-inhibit` unconditionally (see `docs/no-sleep-agents.md`), so a working user systemd
  manager is already an implicit assumption on this host in the normal (desktop/wezterm) case
  — this guard only protects the abnormal case.
- `--quiet` suppresses the `Running as unit: ...; invocation ID: ...` banner `systemd-run`
  prints to stderr on every launch, which would otherwise appear before every interactive
  session.

**`modules/home/services/claude-session-reaper.nix`** — new file, modeled directly on
`cache-cleanup.nix`/`mail-sync-timer.nix`:

```nix
{ config, pkgs, ... }:
{
  systemd.user.services.claude-session-reaper = {
    Unit = {
      Description = "Reap abandoned claude-*.scope units (liveness-only, never CPU/mem/time-based)";
    };
    Service = {
      Type = "oneshot";
      ExecStart =
        let
          script = pkgs.writeShellScript "claude-session-reaper" ''
            export PATH="${config.home.homeDirectory}/.nix-profile/bin:/run/current-system/sw/bin:$PATH"
            echo "claude-session-reaper: starting"
            # ... enumerate 'claude-*.scope' units, check cgroup.procs, stop abandoned
            # ones only; every step tolerant of races (unit gone, proc gone) via || true.
            echo "claude-session-reaper: done"
          '';
        in
        "${script}";
    };
  };

  systemd.user.timers.claude-session-reaper = {
    Unit = {
      Description = "Timer for claude-*.scope reaper";
      Requires = [ "claude-session-reaper.service" ];
    };
    Timer = {
      OnCalendar = "*:0/10"; # every 10 minutes; liveness-only predicate makes frequency safe
      Persistent = true;
      RandomizedDelaySec = 60;
    };
    Install = {
      WantedBy = [ "timers.target" ];
    };
  };
}
```

Add `./services/claude-session-reaper.nix` to the "Service modules" block in
`modules/home/default.nix`, alongside the existing five entries.

Because the reap predicate is liveness-only (never wall-clock), the timer interval is a pure
responsiveness/overhead tradeoff, not a safety parameter — a runaway orphan sits burning CPU
for at most one interval after its session dies, same shape as the 15-minute
`mail-sync-timer` and weekly `cache-cleanup`. 10 minutes is a reasonable starting point given
the thermal severity described in the incident (99°C sustained); this is a tunable, not a
correctness-relevant value, and can be adjusted without any other design change.

### Community Patterns

- The general shape "`systemd-run --user --scope` to contain an externally-spawned process
  tree, `systemctl --user stop` to reap it" is the standard, documented use of scope units
  (`systemd.io/CGROUP_DELEGATION`, `systemd-run(1)`) — this is exactly what container
  managers and per-session process trackers (e.g. `systemd-logind` itself for login
  sessions) do, just applied here to a CLI tool instead of a login session. No unusual or
  unsupported pattern is being introduced.
- The "abandoned" `ActiveState` that systemd scopes can reach when their originating manager
  process disappears (documented for the `Abandon()` D-Bus method) is a related but distinct
  concept from what this task's already-proven mechanism relies on — that D-Bus call is
  typically only invoked by dedicated scope-manager daemons (like `systemd-logind` or
  `systemd-machined`), not by plain `systemd-run --scope` usage, so this research does not
  recommend depending on `ActiveState=abandoned` as the reap signal. The `cgroup.procs`-based
  liveness check (task brief mechanism 3, refined above) is the correct, already-verified
  signal and should remain the sole predicate.

### Recommendations

1. Wrap `packages/claude-code.nix` in `systemd-run --user --scope --unit="claude-$$-$(date
   +%s)" --quiet`, with a `command -v systemd-run` / `XDG_RUNTIME_DIR` fallback guard, and no
   `--pty` (invalid with `--scope`, and unnecessary — cwd/env/tty/exit-code all inherit
   correctly without it, confirmed live above).
2. Implement the reaper as `modules/home/services/claude-session-reaper.nix`, wired into
   `modules/home/default.nix`'s service-modules import list, following the
   `cache-cleanup.nix`/`mail-sync-timer.nix` oneshot+timer shape exactly (PATH export,
   start/done echo lines, `Persistent = true`, tolerant of races).
3. Reap algorithm: enumerate `claude-*.scope` units only -> read each one's `cgroup.procs` ->
   check only those specific PIDs' `/proc/<pid>/cmdline` against a claude-process signature ->
   stop only if zero matches. Never touch CPU time, RSS, or process age. Never run a
   system-wide `pgrep`/`ps`.
4. The opt-out for deliberately-detached work needs no special-case code: anything started as
   its own top-level unit (`systemd-run --user --unit=<name> -- <cmd>`, a name that does not
   match `claude-*.scope`) is untouched by both the wrapper (which only ever wraps `claude`
   itself) and the reaper (whose enumeration glob is `claude-*.scope`). Document this
   explicitly in a comment in the reaper module and/or a short note in
   `docs/no-sleep-agents.md`-adjacent documentation, since it's the kind of thing a future
   reader (or the user, mid-incident) needs to be able to find quickly.
5. Before enabling by default, perform the live interactive smoke test the task brief already
   requires (launch a real session, confirm children land in a distinct cgroup, kill the
   session, confirm the orphan dies) and additionally exercise Ctrl-C, Ctrl-Z, and terminal
   resize during a live interactive turn, since process-group/job-control semantics for
   scope-contained foreground processes are not explicitly documented and were not verified
   in this research pass.
6. Confirm during implementation whether `--collect` on the wrapper's `systemd-run` call
   causes cleanly-completed sessions' scope units to auto-unload (expected, per the generic
   "transient units" wording, but not scope-specific in the docs) — this is a hygiene
   optimization only, not required for reaper correctness.

## Decisions

- Unit type: **scope** (not service, not slice) — confirmed correct by both the task's own
  proven mechanism and by systemd's documented purpose for the unit type.
- Unit naming: **wrapper-generated `claude-$$-$(date +%s)`**, not derived from the CLI's own
  `session_id` — the latter isn't known until after the CLI process starts, i.e. after the
  wrapper would need to have already chosen the unit name.
- Reap predicate: **cgroup.procs membership + per-PID cmdline check, scoped to one unit's own
  process list at a time** — not `ActiveState=abandoned` (unreliable signal for
  non-D-Bus-managed scopes) and not any CPU/memory/wall-clock threshold (explicitly
  prohibited by the binding safety constraint).
- No `--pty`: confirmed invalid/unnecessary for `--scope` mode.

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Wrapper's `systemd-run` dependency breaks `claude` launch entirely in an environment without a working user systemd manager | Guard with `command -v systemd-run` / `XDG_RUNTIME_DIR` check, fall back to bare `exec` |
| Reaper's `cgroup.procs`/`/proc` reads race against a session ending mid-scan | Every step tolerant of "already gone" (`|| true`, existence checks before reads); treat races as "nothing to reap" |
| Repeat of the `gmail-oauth2.nix` degraded-session incident (a periodic unit that fails every run) | Reaper script never treats a missing unit/PID as a hard error; oneshot `Type` with tolerant shell, matching precedent |
| Process-name matching (`cmdline` substring) misses a claude process using a differently-named entry point in a future CLI release, causing a live session's scope to be wrongly reaped | Scope the substring check broadly enough (`claude|@anthropic|opencode`-style, matching the repo's existing precedent) and treat this as a live-verification item before enabling by default; if ever uncertain, the safer failure mode is "never reap" (leaves a false-abandoned scope alive a bit longer), not "reap a live session" — the algorithm above already defaults to skip on ambiguity since it requires *zero* matches, not a specific expected match, to trigger the kill |
| MCP servers or other legitimate children killed along with an actually-abandoned session | This is a deliberate, desired within-session outcome per the task's own root-cause description (mechanism 2 is explicitly relied upon to kill "everything remaining"); MCP servers spawned as children of `claude` are meant to die with their owning session |
| Nested `claude` invocation behaves unexpectedly | Documented as benign self-consistent behavior (inner invocation migrates to its own sibling scope) — not expected to occur via this repo's own tooling (subagents are in-process, not new OS processes) |
