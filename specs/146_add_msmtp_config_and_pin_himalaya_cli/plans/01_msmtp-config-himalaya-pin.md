## Overview

Two independent-in-purpose but file-overlapping changes to the home-manager email stack. First,
freeze the Himalaya CLI at v1.2.0 by adding a dedicated flake input at the nixpkgs revision
`nixpkgs-unstable` is locked to today and exposing it through an overlay as `pkgs.himalaya`, so a
later `nix flake update` cannot pull the 2.x source that has no `oauth2`/`keyring` features and a
different command tree. Second, declare `~/.config/msmtp/config` through `programs.msmtp` with a
gmail and a logos account selected by envelope-from, and drop the bare `msmtp` package line.
Done means: `nix flake check` is green, both home-manager paths build, the rendered msmtp config
matches the specified contents, the himalaya store path is unchanged, and the user has the list
of live msmtp checks that an agent is not permitted to run.

## Risks & Mitigations

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| mail-guard denies a Bash call that merely mentions a guarded token (a commit message, a heredoc, a search pattern with a whitespace-delimited `msmtp` or `secret-tool`, or doc text quoting a denied himalaya subcommand) | M | H | Author every file whose content contains these tokens with the Write/Edit tools, never a Bash heredoc. In Bash, keep the token glued to another character (`msmtp.nix`, `msmtp/config`, `'msmtp'` inside a regex alternation). Phase names below are worded so the derived commit messages contain no bare token. Never route around the hook by store path or wrapper. |
| New files invisible to flake evaluation until tracked by git | M | H | `git add -- <explicit file>` for each new `.nix` file before the first `nix eval` / build in its phase. |
| Pinned input does not reproduce the installed store path | M | L | Phase 1 compares the evaluated out path before and after the change; a mismatch is investigated (overlay argument, feature flag order), not accepted. |
| deadnix / statix / nixfmt flake checks fail on the new overlay or module | L | M | Underscore-prefix unused overlay arguments; run `nixfmt` on touched files; `nix flake check` in every code phase. |
| home-manager activation collides with an unmanaged `~/.config/msmtp/config` | M | L | Phase 4 checks for a pre-existing non-symlink file before switching; if present, stop and report rather than overwrite or move it. |
| Logos send fails on hosts without the Bridge CA | L | M | Same behaviour aerc has there; recorded in the module header comment and docs. |
| Unmatched From address falls through to gmail | L | L | Accepted (two known addresses; task asks for a default); recorded in docs. |
| Frozen himalaya closure gets no library security updates | L | M | Accepted; wrappers use the maildir backend only. The `flake.nix` comment states the condition for moving the pin. |
| A prose comment in the module repeats a literal that a rendered-file occurrence check counts | L | M | Phase 2 assertions target full config lines (`from ...`, `port ...`), and the module comment sits outside `configContent`, so it never reaches the rendered file. |

## Decisions

- **Pin via dedicated flake input plus overlay**, not `src`/`cargoHash` override or a vendored
  derivation: it is the only option that freezes the Rust toolchain with the source and the only
  one verified to reproduce the installed path.
- **Overlay in its own file `overlays/himalaya-pin.nix`**, curried like
  `overlays/unstable-packages.nix`, so neither `lib/mkHost.nix` nor `hmExtraSpecialArgs` needs a
  new argument and `email-tools.nix` refers to plain `himalaya`.
- **Keep `--features=oauth2,keyring`** to preserve the derivation exactly.
- **`passwordeval` uses bare `secret-tool`**, matching aerc, mbsync, and himalaya; the store-path
  form is not adopted, to keep one convention across the four clients.
- **Phases 1 and 2 are sequential** although logically independent: both edit
  `modules/home/packages/email-tools.nix`.
- **Activation**: Phase 4 runs the user-level `home-manager switch --flake .#benjamin`, since
  that generation owns `~/.nix-profile` and the generated config file; the system-level switch
  is left to the user.
- **Tier justifications name `nix flake check`** as the covering check. This is a deploy-consumer
  repository with no `agent-system/` source store, and `verify-touched.sh` was deliberately not
  run at plan time over `.nix` paths (an unmapped path can fall back to a complete battery run).
  The repository's own gate for Nix edits is the flake's check set (statix, deadnix, nixfmt,
  shellcheck, and the standalone home-manager evaluation check), which is a repository-specific
  criterion run directly.

## Rollback/Contingency

Each phase is one commit, so a failed phase is undone with `git revert <phase commit>`; Phase 1
and Phase 2 revert independently in reverse order (Phase 2 first, since both touch
`email-tools.nix`). After reverting an activated change, run
`home-manager switch --flake .#benjamin` again, or `home-manager switch --rollback`, to restore
the prior generation; the generated `~/.config/msmtp/config` symlink disappears with it. If the
pinned input cannot reproduce the baseline store path and the cause is not found within the
phase, stop with the phase marked `[BLOCKED]` rather than falling back to a `src`/`cargoHash`
override. Discarding uncommitted work, if ever needed, follows the snapshot-then-rollback recipe
in `context/contracts/recovery.md`'s rollback rung.
