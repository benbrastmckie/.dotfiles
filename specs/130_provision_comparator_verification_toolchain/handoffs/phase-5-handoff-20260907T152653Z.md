# Phase 5 Handoff: comparator-lean4export-resolve resolver

**Immediate Next Action**: Phase 3 (offline lake-dependency vendoring scratch verification for
comparator.nix), then Phase 4 (packages/comparator.nix).

**Current State**: Phase 5 completed. `packages/lean4export.nix` (a `writeShellApplication`)
builds cleanly (passes shellcheck) as `comparator-lean4export-resolve`, registered in
`overlays/unstable-packages.nix`. Behaviorally verified end-to-end against real elan/lake builds:
- `--help` prints contract documentation.
- Cache miss against `/tmp/comparator-check` (real clone, lean-toolchain=v4.34.0-rc2) triggered a
  real `git clone` + `lake build lean4export` (elan fetched v4.34.0-rc2 on demand), producing
  `~/.cache/comparator/lean4export/leanprover-lean4-v4.34.0-rc2/{lean4export,lean4export.toolchain}`.
  This cache entry is INTENTIONALLY LEFT IN PLACE for Phase 7's fixture runs to reuse.
- Cache hit re-run returned the same path in ~9ms.
- Resolved binary run with `--help`: lean4export has no true `--help` flag (confirmed by reading
  its `Main.lean` -- any `--xxx`-shaped arg is treated as an internal opt, not a flag parser);
  the actual output is a JSON metadata line (`{"meta":{"exporter":...,"lean":{"version":"4.34.0-rc2"}}}`),
  which is real, deterministic, exit-0 output proving the binary runs and reports the correct
  Lean version -- documented as such rather than claimed to be conventional "usage" text.
- Distinct-toolchain test (scratch `v4.31.0` target) resolved to a distinct cache slot; that
  scratch slot was removed afterward (not needed for Phase 7).
- Mismatch demonstration: hand-tampered a sidecar file to a bogus toolchain string and re-ran the
  resolver against the same target -- it refused (exit 1, distinguishing message), rather than
  returning the (now-mismatched-per-sidecar) cached binary. Sidecar restored afterward.
- Deliberately-broken build (`leanprover/lean4:v0.0.0-does-not-exist`) exits 1 with the real
  `lake`/elan error on stderr and empty stdout.

**Key Decisions Made**:
- `writeShellApplication` over raw `writeShellScriptBin` for the shellcheck gate.
- Default pinned lean4export rev: `411dce7db58a3afc60ecab2d211acd1042b593dc` (its HEAD as of this
  packaging), overridable via `COMPARATOR_LEAN4EXPORT_REV`.
- Added `COMPARATOR_LEAN4EXPORT_CACHE` (not explicitly required by the plan, but needed for
  test isolation and useful for Phase 7).
- The resolver depends on `elan`/`lake`/`git` via `runtimeInputs` (nixpkgs' `elan`, wrapped via
  makeWrapper by `writeShellApplication`) -- it does NOT rely on the user's `~/.elan` install,
  though in practice both resolve to compatible behavior on this host.

**Deviations from Plan**: None beyond the writeShellApplication vs writeShellScriptBin
implementation-detail swap (same package family, does not change plan-declared interface/behavior)
and the added CACHE env var.

**What NOT to Try**: Don't expect a literal "usage:" string from `lean4export --help` -- it has
no such flag; its response to any `--xxx` arg is metadata JSON. Don't delete
`~/.cache/comparator/lean4export/leanprover-lean4-v4.34.0-rc2/` -- Phase 7 fixture runs reuse it.
