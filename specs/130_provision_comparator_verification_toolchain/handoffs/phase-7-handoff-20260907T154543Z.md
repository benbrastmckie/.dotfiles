**Critical finding requiring Phase 8 documentation**: elan-installed Lean toolchains on this host
ship `bin/lake` as a bash-shebang wrapper script (LEAN_CC injection), which breaks landrun's
`--ldd` auto-detection (ELF-only, no shebang following) -> Landlock denies the nested bash
execve -> `permission denied`. This is an ENVIRONMENT failure, not a verdict, and was correctly
not recorded as a rejection (confirmed via `LANDRUN_LOG_LEVEL=debug` root-causing before
proceeding). Fix: use `lean-toolchain-bin` (Phase 2's raw-ELF, autoPatchelf'd toolchain) on PATH
instead of elan's own toolchain when checking a `v4.34.0-rc2` project. This must be documented in
Phase 8 as an operational requirement for comparator callers on this host, alongside the five
originally-mandated decision records.

**Key Decisions Made**: Both fixtures resolve lean4export to the SAME cache slot
(`leanprover-lean4-v4.34.0-rc2`, already built in Phase 5) since Comparator's own fixtures target
its own toolchain -- no new resolver build needed for Phase 7.

**Deviations from Plan**: None in scope/approach; the landrun/elan-wrapper-script debugging
detour was necessary investigation, not a plan deviation (the plan's own Testing & Validation and
Risk table anticipated "a build that merely succeeds ... does not verify this phase" -- exactly
the discipline that caught this).

**What NOT to Try**: Don't invoke `comparator`/`lake build` for a landrun-sandboxed step while
`lake`/`lean` resolve (via PATH) to an elan-managed toolchain's wrapper-script `bin/lake` -- it
will fail with a misleading generic "permission denied" that is NOT a rejection verdict.
