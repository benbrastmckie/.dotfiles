# Phase 2 Handoff: Lean v4.34.0-rc2 toolchain acquisition

**Immediate Next Action**: Phase 5 (comparator-lean4export-resolve resolver) or Phase 3
(offline lake-vendoring scratch verification) -- both are wave-1/wave-2 independent of each
other; proceeding to Phase 5 next since it has no dependency, then Phase 3 -> Phase 4.

**Current State**: Phase 2 completed. `packages/lean-toolchain-bin.nix` builds via a real FOD
(`fetchurl` of `lean-4.34.0-rc2-linux.tar.zst`, hash confirmed from GitHub's own release-asset
digest) plus an offline `autoPatchelfHook` unpack/relocate step. Verified:
`$out/bin/lean --version` -> "Lean (version 4.34.0-rc2, ...)"; `$out/bin/lake --version` ->
"Lake version 5.0.0-src+6a10ac8 (Lean version 4.34.0-rc2)". `flake.nix`'s unused `lean4` input
resolved via comment-and-keep (not pinned/used); `nix flake check` passes.

**Key Decisions Made**:
- Route (i) (prebuilt release tarball) was available and used; route (ii) (elan-mediated FOD)
  was not needed.
- Used `autoPatchelfHook` rather than nix-ld for the prebuilt binaries, since this is a real
  Nix derivation with buildInputs available (gmp, libuv, stdenv.cc.cc.lib), not a
  `~/.elan`-managed foreign binary the way `nix.nix`'s existing nix-ld handling targets.
- `flake.nix`'s `lean4` input: comment-and-keep, not pin-and-use -- it floats on lean4 default
  branch and building Lean from source is explicitly a non-goal.

**Deviations from Plan**: None (all plan tasks completed as specified).

**What NOT to Try**: Don't assume `nix.nix`'s existing nix-ld wiring covers this derivation's
binaries -- they're patched via autoPatchelfHook at build time instead, which is why they work
without nix-ld.
